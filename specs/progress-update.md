- Feature 81: GlbViewer screenshot bridge (`components/viewer/glb-viewer.tsx`) — Added an optional `onScreenshotterReady(capture)` prop. If the source canvas is larger than the requested `maxSize` (default 512 px), the bridge first downscales via an offscreen `<canvas>` `drawImage(..., w, h)` so the PNG payload stays under 200 KB.   - **Two states tracked**: `modelReady` (flips when `ConfigurableViewer`'s existing `onFirstFrame` callback fires — i.e. `useGLTF` resolved + scene traversal + material upgrade is complete) and `showLoader` (stays true for an extra 350 ms after `modelReady` so the fade-out animation can complete before unmount). ### Augmented Reality Place-in-Room (cross-sprint)

- Feature 95: WebXR place-in-room — a "Place In Room" action lets a customer place a life-size AR instance of the product on a real floor/tabletop, viewed through the phone camera. Shipped as WebXR-only (Android Chrome/Edge on ARCore-class hardware); this was a scoped-down version of the AGENTS §9 "AR place in room" line item, which is now moved into §3.3 as a shipped feature. iOS AR (Apple Quick Look via USDZ) remains out of scope — it needs a GLB→USDZ conversion stage in the upload pipeline that wasn't built in this pass.
  - `components/viewer/ar-viewer.tsx` — new client component, dynamically imported (`ssr:false`) so `@react-three/xr` never lands in the initial product-page bundle. Uses `createXRStore({ hitTest: true, domOverlay: true, controller: false, hand: false })` from `@react-three/xr` (installed this pass). Entering the session requires an explicit "Enter AR" tap inside the already-mounted overlay (not auto-triggered on mount) — `store.enterAR()` needs `<XR>` to have attached Three's `WebXRManager` at least once and needs to run inside a direct user gesture, both of which an eager `useEffect` call can race. A continuous `useXRHitTest(fn, "viewer", ["plane", "point"])` drives a reticle (a `RingGeometry` with `matrixAutoUpdate={false}`, matrix set directly from the hit-test result each frame — the standard three.js AR-reticle pattern) that tracks whatever floor/tabletop the camera points at; accepting raw `"point"` hits alongside classified `"plane"` hits lets it lock on before ARCore finishes full plane classification. Tapping "Place here" (rendered via `<XRDomOverlay>`, the WebXR `dom-overlay` feature that puts real HTML on top of the camera passthrough) decomposes the last hit matrix into a position/quaternion and locks the model there. Once placed, a **full-screen touch layer** in the same dom-overlay (behind the button rows in paint order, so buttons still get their own taps) reads raw `touchstart`/`touchmove`/`touchend` — one-finger drag repositions the model along the floor (screen delta converted to a world-space offset via the camera's current right/forward vectors projected onto the floor, normalized to screen width so it feels consistent across phones) and two-finger pinch-and-twist rescales it (distance ratio vs. gesture-start distance) and spins it around its vertical axis in the same gesture (angle delta between the two touches, via `atan2`, applied as a world-Y-axis quaternion rotation — turns the object to face a new direction rather than tilting it, which is what a camera-axis rotation would do instead); both re-baseline whenever the active finger count changes so lifting/adding a finger mid-gesture never jumps. `+`/`-` buttons remain as a coarse scale fallback alongside the gestures; "Move" unlocks back to reticle mode for a full re-placement. Exiting (✕ button or the OS/browser's own AR-exit chrome) is detected via `xrStore.subscribe` diffing `prev.session` against `state.session` and calling the `onClose` prop either way — one code path for both exit routes.
  - **Carries over the customer's current look "for free"**: the AR component reads the same `viewer` Redux slice (`color`, `partColors`, `finish`, `textureUrl`) the on-page configurator already writes to, so whatever the customer had picked immediately before tapping "Place In Room" is what shows up in AR — no props to thread through, just two components subscribed to the same store.
  - **Scene isolation**: `useGLTF` caches the parsed GLTF scene by URL, and the on-page `ConfigurableViewer` (still mounted behind the full-screen AR overlay, though hidden — see below) mutates that shared scene's mesh materials in place. The AR component clones the scene (`gltf.scene.clone(true)`) before re-traversing and upgrading materials, so the two viewers never fight over the same material instances. `product-configurator.tsx` also stops rendering `ConfigurableViewer` entirely while `arOpen` (`!arOpen &&` guard) — avoids a second live WebGL context competing with the AR session on mobile GPUs, on top of the scene-clone isolation.
  - **Floor-anchored placement**: GLB authoring pivots vary (centered, base-at-origin, etc.), so the AR scene builder computes a `THREE.Box3` over the cloned scene once and offsets it by `-box.min.y` inside the placed group — the model's visual base always rests on the tapped surface regardless of how the source asset was modeled.
  - **Shared material helpers extracted** to `lib/viewer/material.ts` (`FINISH_MAP`, `copyMaterialSafely`, `upgradeToPhysical`, `derivePartId`) — previously private to `configurable-viewer.tsx`. `ConfigurableViewer`'s own behavior is unchanged (pure relocation, verified by type-check + build); `ARViewer` imports the same table so a "Matte" pick, say, resolves to the identical roughness/metalness/clearcoat numbers in both the on-page viewer and AR. `derivePartId` in particular has to produce byte-identical keys to what `ConfigurableViewer` dispatches via `setParts` — both derive `name:${materialName.toLowerCase()}` (falling back to `mesh:${uuid}:${index}`) — otherwise `viewer.partColors[partId]` lookups in AR would silently miss.
  - **Feature detection, not a try-and-fail button**: checks `navigator.xr?.isSessionSupported("immersive-ar")` in a `useEffect` on mount and only renders the "Place In Room" pill (top-right of the viewer frame, shown once `modelReady`) when it resolves `true`. Only that one-line check runs eagerly — `@react-three/xr` and the rest of `ar-viewer.tsx` load on demand through the existing `dynamic(..., { ssr: false })` pattern already used for the other viewer components, so devices that can't do AR (all of iOS today) pay zero extra bundle cost. **Updated 2026-08-16**: this check, the button, and the portal now live in `components/viewer/ar-launcher.tsx` rather than directly in `product-configurator.tsx` — see Feature 96 below. `ar-viewer.tsx`'s own runtime behavior is unchanged.
  - `ARViewer` mounts through `createPortal(..., document.body)`, now issued from `ar-launcher.tsx`, so its `fixed inset-0` overlay can't be clipped by any ancestor that happens to establish a new containing block.

### Virtual Try-On, wrist (watches) + foot (shoes) (cross-sprint)

Goal: a second AR mode for products that don't suit "place a life-size copy on the floor" — watches and shoes. Room AR stays exactly as it was for every other category; try-on renders the product directly on the customer's own wrist or foot using camera-based landmark tracking instead of WebXR SLAM (WebXR doesn't expose hand/foot landmarks, so this is a parallel pipeline, not a `@react-three/xr` extension). **Not yet verified on a physical device** — same caveat Room AR shipped with initially; several of the math steps below are flagged as assumptions pending on-device validation.

- Feature 96: `Category.tryOnAnchor` — migration `20260816120000_add_category_try_on_anchor` adds a `TryOnAnchor` enum (`WRIST | FOOT`) and a nullable `Category.tryOnAnchor` column. Set once at category-create time via a new `<select>` on `/admin/categories`' create form (`category-form.tsx` + `actions.ts`); categories have no edit action today, so this is create-time only, same as `name`. Every product under a category with `tryOnAnchor` set automatically gets the try-on mode — no product-level field, no per-product code change needed for future categories (e.g. a future "Rings" category just needs an admin to pick `WRIST` — or a new anchor value — at creation). `/admin/categories` lists the resolved AR mode per category. `app/products/[slug]/page.tsx`'s `loadProduct()` now includes `category: { slug, name, tryOnAnchor }` and threads it through to `ProductConfigurator`.
- Feature 97: Shared styled-scene extraction (`components/viewer/use-styled-scene.ts`) — the `useStyledScene` hook that clones the product's GLTF scene and applies the customer's current `color` / `partColors` / `finish` / `textureUrl` from the `viewer` Redux slice was pulled out of `ar-viewer.tsx` verbatim (pure relocation, zero behavior change — `ar-viewer.tsx` now just imports it) so both Room AR and the new try-on pipeline render an identical customer-styled model.
- Feature 98: `ARLauncher` (`components/viewer/ar-launcher.tsx`) — the single AR integration point on the product page now, replacing the inline `arSupported`/button/portal block that used to live directly in `product-configurator.tsx`. Resolves to exactly one primary mode from `product.category.tryOnAnchor`: set → "Try On" (gated on `navigator.mediaDevices?.getUserMedia` support, works on iOS too since it doesn't need WebXR); unset → "Place In Room" (gated on the existing `navigator.xr.isSessionSupported("immersive-ar")` check, Android-only, byte-identical to the pre-existing behavior). The one place both can coexist: if try-on's camera permission is denied *and* the device also supports WebXR, the try-on overlay surfaces an explicit "Use Room Placement instead" button that flips `ARLauncher`'s internal `mode` state without closing the overlay — never shown up front, only as an error-recovery escape hatch. `product-configurator.tsx` still owns the `arOpen` boolean (so its existing `!arOpen &&` guard that unmounts `ConfigurableViewer` while any AR overlay is open is untouched) and just delegates *which* button/mode renders to `<ARLauncher>`.
- Feature 99: Try-on pipeline (`components/viewer/tryon/*`, `lib/viewer/tryon/*`) — `getUserMedia` (rear camera, `facingMode: "environment"`, explicitly started from a "Start Try-On" tap inside the mounted overlay rather than on mount, mirroring Room AR's existing `enterAR()`-needs-a-gesture fix) feeds a MediaPipe Tasks Vision `HandLandmarker` (wrist) or `PoseLandmarker` (foot, up to 2 feet) running its own `requestVideoFrameCallback` loop (guarded on `video.currentTime` so it never re-runs on a stale frame). Both anchor hooks (`use-wrist-anchor.ts`, `use-foot-anchor.ts`) return the same shape — `{ position, quaternion, scale, confidence, status }` — written to a ref every detection tick (not React state, to avoid re-rendering at detection rate) so `TryOnScene`'s `AnchoredModel` helper can bind whichever frame it's given to a `matrixAutoUpdate={false}` `<group>` (same manual-matrix pattern as the existing hit-test reticle) with per-frame lerp/slerp smoothing (`smoothing.ts`), without ever knowing which anchor produced it. `useStyledScene` (Feature 97) supplies the customer-styled clone; a `Box3` measurement of that clone's own footprint, divided into a fixed real-world reference size (`WATCH_CASE_DIAMETER_M` for watches; the selected UK shoe size converted to centimeters for shoes), gives the real-world scale factor — same "measure the model, don't trust its authored scale" approach the existing floor-offset logic already uses.
  - **Wrist math**: rotation basis from HandLandmarker's metric `worldLandmarks` (wrist=0, index MCP=5, pinky MCP=17) — `along` = wrist→knuckle-midpoint, `across` = index↔pinky, `palmNormal` = their cross product, re-orthogonalized. Position comes from a pinhole-camera depth estimate off the apparent pixel width between the two knuckle landmarks vs. a fixed `PALM_WIDTH_M` reference, then unprojected via **direct pinhole math** (`lib/viewer/tryon/camera-math.ts`), deliberately not `THREE.Vector3.unproject(camera)` (that expects a non-linear NDC depth from near/far planes; we already have a linear metric depth). Offset back `WATCH_BACK_OFFSET_M` along `−along` so the case sits on the wrist, not the palm.
  - **Foot math**: same depth technique, generalized from palm-width to heel↔toe apparent pixel span vs. the real length implied by the customer's picked size (`UK_SIZE_REFERENCE_CM` / `UK_SIZE_STEP_CM`, anchored at UK9≈27cm) — **this specific generalization isn't in the original design brief (which only specified the wrist depth formula) and is flagged for on-device validation**. Rotation basis from ankle/heel/toe (27-32). Confidence gating is mandatory (PoseLandmarker degrades badly on feet-only framing): a foot only reaches `"tracking"` after `FOOT_STABLE_TRACKING_MS` (~1s) of continuous confidence above `FOOT_MIN_CONFIDENCE`, and drops to `"lost"` immediately on any bad frame rather than letting the model drift. Both feet track independently (`use-foot-anchor.ts` returns one frame per side); the left foot's model is mirrored (`scale.x` negated on its `AnchoredModel`) — flagged as needing an on-device visual check for inverted face culling, with `material.side = DoubleSide` as the documented one-line fix if it looks inside-out.
  - **Shoe size is ephemeral** (`size-picker.tsx`) — a UK-size chip picker shown only inside the try-on overlay, plain component `useState`, never written to Redux/the product schema/the cart. Consistent with the existing "customizations are visual previews only" rule.
  - **Occluders**: `forearm-occluder.tsx` (tapered cylinder, child of the wrist's rotated group, extends along local −Y) and `ground-occluder.tsx` (world-aligned horizontal plane, Y-position read from the tracked foot's own anchor frame each tick) are both depth-only (`colorWrite:false`, `depthWrite:true`, `renderOrder:-1`) — same technique class as writing an invisible mask so real product geometry that should be hidden behind the customer's actual arm/the floor gets depth-tested away, revealing the camera passthrough underneath.
  - **Video/canvas aspect alignment** (`tryon-viewer.tsx`): the video is displayed **letterboxed** (`useLetterboxSize`, computed from `video.videoWidth/videoHeight` vs. viewport size) rather than cropped-to-fill, and the transparent `<Canvas>` overlay is sized to that exact same box. This isn't cosmetic — the anchor math estimates position from the *raw* video's pixel coordinates, and R3F's camera aspect auto-tracks whatever container it's given; a cropped (`object-cover`) video would leave the canvas's aspect disagreeing with the coordinate space the landmark math assumes, offsetting every placement.
  - **MediaPipe assets are self-hosted**, never a CDN: the WASM bundle was copied from `node_modules/@mediapipe/tasks-vision/wasm/` into `public/mediapipe/wasm/`, and `hand_landmarker.task` / `pose_landmarker_lite.task` (renamed `pose_landmarker.task`) were downloaded from MediaPipe's official model-storage URLs into `public/mediapipe/models/` — both are committed as static assets (~47 MB total). `lib/viewer/tryon/landmarker-loader.ts` caches both landmarkers behind singleton promises, same pattern as the existing Draco/NodeIO singleton in `lib/glb/process.ts`.
  - **Lazy-loaded, bundle-isolated**: `@mediapipe/tasks-vision` is only ever imported from files under `components/viewer/tryon/` and `lib/viewer/tryon/`, and `ARLauncher` only mounts `TryOnViewer` via `next/dynamic(..., { ssr:false })` — so the multi-MB package and model files are fetched only once a customer on an eligible product actually taps "Try On", never on page load and never at all for non-try-on categories.
  - All tunable constants (`PALM_WIDTH_M`, `WATCH_BACK_OFFSET_M`, `WATCH_CASE_DIAMETER_M`, `CAMERA_FOV_DEG`, UK-size reference/step, confidence thresholds, stable-tracking duration, smoothing factors) live in `lib/viewer/tryon/constants.ts` with a doc-comment table mapping each one to the visual symptom it fixes.

## Architecture Decisions

- Next.js 16 + React 19 + Tailwind v4 (CSS-tokens, no `tailwind.config.js`).
- `proxy.ts` (not `middleware.ts`) per Next 16 rename. Edge-safe `auth.config.ts` imported here; Node-only `auth.ts` does Prisma + bcrypt.
- Prisma 7 driver-adapter mode (`@prisma/adapter-pg`) — `PrismaClient` constructor always requires `{ adapter }`. Generated client at `app/generated/prisma/`; import from `@/app/generated/prisma/client` (no `index.ts` in v7).
- `prisma.config.ts` `datasource.url` reads `DIRECT_URL` so migrations bypass pgbouncer; runtime adapter uses pooled `DATABASE_URL`.
- NextAuth v5 split-config pattern: `auth.config.ts` (edge-safe, no Prisma) + `auth.ts` (Node, adds Prisma adapter and Credentials provider). JWT strategy (no DB sessions needed for our use).
- Tiny UI primitives in `components/ui/` (Button/Input/Label) — no shadcn dependency. `cn()` via `clsx + tailwind-merge`.
- Server-side Draco compression — `@gltf-transform/core` + `draco3dgltf`. `NodeIO` and Draco modules cached behind a singleton promise to avoid re-initializing on every request.
- Pluggable storage driver — S3 today, easy swap to Supabase Storage or local FS later via `lib/storage/index.ts` re-export.
- Upload proxied through a Next.js API route (not presigned direct-upload) so server can validate + Draco-compress before persisting.
- All vendor uploads start as `ProductStatus.PENDING`; admin must approve before public listing surfaces them (per AGENTS §3.7).
- Redux Toolkit for client state (cart, viewer config) — per AGENTS §5. RTK Query deferred until we add real API surfaces in Sprint 7-8.
- Cart persistence via `store.subscribe` + `localStorage` instead of a Redux middleware. Reason: the persistence layer needs to be SSR-safe and run only after providers mount, which is exactly what `useEffect` gives us — a middleware would either fire on the server (unwanted) or require `typeof window` guards inside the dispatch path. Storage key is versioned (`3dmkt:cart:v1`) so future schema bumps can wipe and re-hydrate cleanly.
- Variant overrides applied **scene-wide** to all mesh materials. Variants are a single-axis swap (color / material label / texture) rather than per-mesh slot targeting. Per-mesh targeting is a future expansion if vendors ask.
- Material cloning + originals snapshot pattern in `ConfigurableViewer` so we never mutate the `useGLTF`-cached scene (would bleed between viewer instances and across navigations).
- Every cloned material is **upgraded to `MeshPhysicalMaterial`** (a superset of `MeshStandardMaterial`). Reason: it lets us expose clearcoat without branching by material type. Marginal GPU cost; no functional regression for products that don't use the extra channels.
- Customizations are **visual previews only** — they live entirely in the `viewer` Redux slice and never serialize into the cart or order. Cart line items still carry only `productId` + `variantId`. Reason: the cart is a fulfilment contract and vendors can only ship pre-defined variants. UX surfaces this with a footer note in the controls panel.
- Customization surface is **customer-centric**, not engineering-flavored. We expose named **Finish** presets (Matte / Satin / Glossy / Metallic / Polished) rather than raw roughness / metalness / clearcoat sliders, and named **Lighting** presets (Studio / Daylight / Showroom / Cozy / Evening) rather than HDR file names. Internal `FINISH_MAP` and `LIGHTING_TO_DREI` tables translate at the viewer layer. Reason: a buyer thinks "I want this in matte black under cozy light", not "roughness 0.85 with the `lobby` HDR". The raw axes are still available in the GLB material — we're choosing not to expose them.
- Screenshot capture uses `gl.domElement.toDataURL("image/png")` against the WebGL canvas. This requires `preserveDrawingBuffer: true` in the renderer config — the small memory/perf cost is worth a one-line screenshot button.
- HDR environment preset uses a `key={preset}` remount on drei's `<Environment>`. Reason: drei caches the loaded HDR per-preset; remounting is cleaner than mutating the cached instance and avoids a brief flash when switching.
- Decimal columns (price) always serialized via `.toString()` before crossing the RSC → client component boundary; `JSON.stringify` of a `Decimal` would throw otherwise.
- `next/image` deliberately not used for product imagery until `images.remotePatterns` is configured for the actual S3/CDN host.
- Stripe-hosted Checkout (redirect flow) over Payment Element / embedded checkout. Reason: Stripe handles all wallets (Apple Pay, Google Pay), 3DS, tax, and form layout out of the box — far less code and PCI surface area for an MVP. We give up some UX control over the payment page itself.
- Discounts applied as **single-use Stripe coupons** created server-side per checkout session (one-shot, `duration: "once"`). Reason: keeps our DB the source of truth for promo logic (Stripe coupons are throwaway), and Stripe shows the discount on the receipt with the correct code label. Trade-off: we create a coupon per checkout instead of pre-provisioning them — fine at our scale.
- Server-trusted cart validation. **Never** trust the client's `price` field — `validateCart` re-fetches every product, rejects unapproved or insufficient-stock items, and rebuilds line totals from `Product.price`. Even the Stripe `line_items` are built from server-fetched prices.
- Orders are created **before** the Stripe session (status PENDING with `stripeSessionId` filled in immediately after) so the webhook always has a row to flip. Webhook idempotency is enforced by checking `order.status === "PENDING"` inside the transaction.
- User suspension is a soft block — `User.suspendedAt` is a nullable timestamp checked at sign-in only. Reason: JWT sessions are stateless, so we'd otherwise need to round-trip to the DB on every request. Trade-off: a suspended user with a live session can finish out their token's lifetime (24h default). Hardening pathway (if needed): swap to DB-backed sessions or add a Redis-backed deny-list.
- Admin actions surface "you can't do this to yourself" + "you can't demote/suspend/delete the last admin" guards in `lib/admin.ts` rather than scattering the checks per-action. Result is a single place to audit lockout safety.
- **Vendor approval is the trust gate** (changed 2026-05-25). `Vendor.approvedAt` now drives product `status` at upload time: approved vendor → product created as `APPROVED`; unapproved vendor → product created as `PENDING`. Approving a vendor *also* batch-flips any of their queued PENDING products to APPROVED in the same transaction. Revoking vendor approval intentionally does **not** pull back already-live products — those may already be in customer carts/orders, and silent take-downs would surprise users; admin instead revokes individual listings from `/admin/products?status=approved`. The previous "two-level approval" (vendor + every product) is gone — admin retains an explicit revoke for any listing that needs to come down, but the steady-state for trusted vendors is zero-touch.
- **Revoke / restore re-uses the existing reject/approve actions.** The admin product card's action footer is now a status-driven switch (PENDING → Approve/Reject, APPROVED → Revoke, REJECTED → Restore), but all three states call the same two server actions (`approveProduct` + `rejectProduct`). `rejectProduct` already accepts a reason and stores it in `Product.rejectionReason`; `approveProduct` already clears that reason on success. No new server actions, no new schema column, no new status enum — just relabeling the same flow per current state. Trade-off: the negative-action button is called "Revoke" in the UI but is internally a "Reject" — fine in code (semantically the same write), confusing only if you grep for "revoke" and miss `rejectProduct`. Documented inline.
- **Thumbnails are captured client-side, not server-side.** Three competing options for generating product thumbnails: (a) headless WebGL on the server (`gl` / `headless-gl` — binary builds, hard to bundle on Vercel), (b) Puppeteer + a tiny render page (~250 MB Chromium dependency, multi-second cold starts), (c) client-side R3F screenshot at upload time. We chose (c) because the vendor already sees the live preview during upload — capturing the same canvas costs zero additional rendering, requires no new server dependency, and yields a thumbnail that matches what the vendor saw (correct camera, framing, materials). Trade-offs: a malicious vendor could upload a misleading PNG that doesn't match their GLB (mitigated by storing it under an upload-id-prefixed key so it can't be swapped post-create; admins also see the real GLB in the review queue), and pre-pipeline products keep showing the placeholder icon until re-uploaded. Acceptable for an MVP — a backfill script can generate thumbs for legacy products if needed.
- **Listing surfaces never load GLBs.** Every page that previously embedded `<GlbThumbLazy>` (i.e. that initialised a hidden R3F canvas per product card) now uses the plain `<ProductThumb>` HTML component. WebGL is reserved for *intent-driven* surfaces only: the product detail page (customer wants the full configurator), the upload preview (vendor needs to confirm the model), and the admin review queue (click-to-load 3D, gated on a button press). Result: `/products` first paint went from "load 60 GLBs in parallel" to "load 60 PNGs lazily" — orders of magnitude less network + WebGL initialisation. Schema didn't change; `Product.glbUrl` is still always present, the listing query just stops selecting it.
- Realtime chat uses Supabase **broadcast** (pubsub), not `postgres_changes` (DB-replication-driven). Reason: broadcast doesn't require Realtime to be enabled on the `Message` table and doesn't require RLS policies to gate read access — security is enforced at the Next.js API layer where we already have NextAuth context. Trade-off: realtime fan-out is best-effort; if the broadcast drops, the persisted DB row is still the source of truth and clients see the message on next page load / refresh.
- Chat channels are scoped to `chat:{productId}:{userIdA}:{userIdB}` with the two user IDs **sorted** so both participants land on the same channel name. This is the simplest way to guarantee consistent channel names across the customer and vendor sides without a stored conversation ID.
- Vendor messages list is grouped per (productId, customerId) **in-memory** from the latest 500 messages. Fine at MVP scale; a `Conversation` materialized view or `lastMessageAt` denormalization can replace it once the inbox grows.
- Vendor product **delete** refuses when `_count.orderItems > 0` to preserve purchase history integrity. Soft-delete or "archive" is not modeled yet — vendors can set stock to 0 to hide a product.
- Rejection reason is a free-text string (5-500 chars) rather than a curated enum. Reason: each rejection has unique context (poly count, geometry issue, naming, etc.), and a fixed taxonomy would either be too narrow or too broad. If we later want analytics we can add a `category` enum alongside the free-text field.
- **Design language stays in the zinc family.** The UI polish pass deliberately did **not** introduce a brand accent (no indigo / amber / sky CTA). Reason: an MVP marketplace looks more credible in a tight neutral palette than in a colorful one; semantic accents (emerald=paid, amber=pending, red=destructive, sky=in-transit) carry status only. Headers and cards lean on translucency + soft shadows + subtle gradients rather than color to feel premium.
- **Glass chrome on sticky headers.** All three top-level navigations (`PublicHeader`, vendor layout, admin layout) now use `bg-white/70 backdrop-blur-xl supports-[backdrop-filter]:bg-white/60` with a thin translucent border. Reason: content scrolling beneath the chrome remains legible while the header keeps a sense of elevation. Falls back cleanly when `backdrop-filter` isn't supported.
- **Card elevation tier.** Cards now follow a consistent tier system: `rounded-2xl border-zinc-200/80 shadow-sm shadow-zinc-900/[0.03]` at rest, `hover:shadow-md` + `-translate-y-0.5` on hover for clickable cards. Stat tiles, product cards, dashboard panels all share this language. Internal sub-cards (e.g. variant chips) stay on `rounded-lg`.
- **`.bg-grid-fade` is a single utility** in `globals.css` rather than re-implemented per page. Used by both the landing hero and the auth layout. Implemented as a `radial-gradient` dot pattern with a `mask-image: radial-gradient(...)` so the dots fade to transparent at the edges — no hard cutoff.
- **`tabular-nums` on numeric admin columns** so right-aligned counts and currency don't shift digit-by-digit between rows. Applied selectively (stat groups, alert counts, order totals) rather than globally to avoid affecting prose.
- **Two-layer loading feedback.** Every navigation gets both a *router-level* signal (the top progress bar fires the instant the link is clicked) **and** a *segment-level* signal (Next 16's `loading.tsx` Suspense fallback fills the destination layout while the RSC payload streams). Reason: the bar gives the user immediate "I heard you" feedback even if the destination is server-rendering fast; the skeletons keep the layout from collapsing during long DB queries (e.g. `/products` with 60 rows + variant counts). The two layers complement rather than duplicate.
- **Route progress detection uses anchor-click capture + history-method patching, not `useLinkStatus`.** `useLinkStatus` is per-Link, which would require wrapping every `<Link>` in a custom component. The document-level click listener + monkey-patched `history.pushState` / `replaceState` covers Links, programmatic `router.push`/`router.replace`, and back/forward via `popstate` in one place — and we only need it for the global progress bar. Trade-off: we mutate a global (`window.history.*`); the cleanup function in `useEffect` restores the originals.
- **Skeletons mirror the destination layout exactly**, not generic "grey rectangles". `/products/loading.tsx` renders 8 cards in the same responsive grid as the live page; `/products/[slug]/loading.tsx` renders the 2-column configurator split. Reason: prevents layout shift on commit — the page composes the moment data arrives, no reflow. The cost is a small amount of duplicated layout structure between the page and its loader.
- **`PageLoader` vs skeleton choice.** Use `PageLoader` (full-screen brand glyph + spinner) when the destination *has no chrome above it* — root `app/loading.tsx`, the `(auth)` route group, `/checkout` and `/checkout/success` (where the page replaces, doesn't compose with, a content grid). Use **skeletons** when a layout chrome (header / nav) keeps rendering above, so the user sees continuity. Mixing them flat-out (e.g. `/products` showing a centered brand spinner) would feel jarring against the persistent `PublicHeader`.
- **AR "place in room" is WebXR-only, feature-detected, and scoped to Android in this phase.** Three options existed: (a) WebXR hit-test AR (works on Android Chrome/ARCore; zero new server pipeline, reuses the existing GLB directly), (b) also add iOS Apple AR Quick Look (needs a GLB→USDZ conversion stage, a new stored asset type, and iOS doesn't support WebXR so the two paths would need entirely separate UI/trigger code), (c) a third-party all-platforms wrapper like `<model-viewer>` (pulls in a parallel rendering stack alongside the project's existing React Three Fiber pipeline). Chose (a): fastest to ship, no new asset pipeline, and it reuses 100% of the existing GLB/material/Redux-customization stack. The entry button is feature-detected via `navigator.xr?.isSessionSupported("immersive-ar")` and hidden entirely (not shown-and-broken) where unsupported — iOS Safari today. (b) is documented as deferred future work in both AGENTS §9 and this file's backlog.
- **AR scene is a clone, not a live share, of the product's cached GLTF scene.** `useGLTF` caches parsed scenes by URL; `ConfigurableViewer` (on-page) mutates that shared scene's materials in place. Since the AR overlay can open while the on-page viewer is still mounted underneath, cloning (`gltf.scene.clone(true)`) before re-traversing avoids both components racing to reassign `mesh.material` on the same underlying node. `product-configurator.tsx` additionally stops rendering `ConfigurableViewer` while AR is open, both to avoid a second live WebGL context on mobile GPUs and as defense-in-depth alongside the clone.
- **AR customization carries over via the existing global Redux store, not props.** `ARViewer` reads the same `viewer` slice (`color`, `partColors`, `finish`, `textureUrl`) the configurator already writes to — no new plumbing needed for "AR shows what the customer had just picked." The trade-off: `derivePartId` (now shared in `lib/viewer/material.ts`) must produce identical part-id keys in both places, since `viewer.partColors` is keyed by that id — verified by extracting one shared function rather than hand-copying the derivation logic into `ar-viewer.tsx`.
- **In-viewer 3D loader uses the PageLoader visual, scoped to the canvas frame.** The product-detail page's `<ViewerLoader>` (in [app/products/[slug]/product-configurator.tsx](../app/products/%5Bslug%5D/product-configurator.tsx)) re-implements the brand-glyph + rotating-ring + animated-dots pattern from the global `PageLoader` rather than importing it, because PageLoader's `min-h-screen` / `min-h-[60vh]` sizing and full-bleed `bg-grid-fade` backdrop don't fit a constrained container. Same animations (`@keyframes spin`, `@keyframes loader-dot`), same brand glyph, scaled down with a `from-zinc-50/95 via-white/95 to-zinc-100/95 backdrop-blur-sm` background so it reads as the viewer's own surface, not an overlay. Trade-off accepted: a small amount of duplicated JSX for a much better visual fit. If a third constrained-container loader ever shows up, factor a shared `<InlineLoader>` primitive at that point.
- **Virtual try-on's category gate lives on `Category`, not `Product`.** Three options existed for deciding which products get "Try On" vs. "Place In Room": (a) a `tryOnAnchor` column on `Category`, set once per category, inherited by every product under it, (b) a denormalized column on `Product` derived from category at upload/edit time (mirrors how `status` derives from `vendor.approvedAt`), (c) a hardcoded category-name check (`name === "Watches"`). Chose (a): a future category (e.g. rings, sunglasses) opts in with one admin form field and zero code changes, and there's no per-product override UI planned that (b) would justify building. Trade-off: categories have no edit action today (only create/delete), so `tryOnAnchor` is create-time only — same limitation `name` already has.
- **Watch scale uses a fixed constant, not a per-product vendor field.** `WATCH_CASE_DIAMETER_M` in `lib/viewer/tryon/constants.ts` is one number applied to every watch, rather than a new `Product.caseDiameterMm` field with vendor-facing upload/edit UI. Chosen for scope: real-world accuracy per product is a nice-to-have, not a launch blocker, and the schema/form surface it would need (plus validation, plus handling for pre-existing products missing the field) is disproportionate to a first pass. If per-product accuracy is needed later, the field slots into the existing vendor upload/edit forms next to `title`/`price`.
- **Shoe size is ephemeral, never persisted.** The UK-size picker shown inside try-on lives entirely in component `useState` — not Redux, not `Product`/`ProductVariant`, not the cart. This mirrors the existing "customizations are visual previews only" rule (color/finish/lighting never serialize into the cart either); a real size-driven purchase flow (size affecting stock/SKU) is a separate, larger feature this doesn't attempt.
- **Try-on is a parallel pipeline, not a `@react-three/xr` extension.** WebXR's hit-test API gives device SLAM tracking (planes, anchors) but no hand/foot/body landmarks — there's no way to ask a WebXR session "where is the user's wrist." Try-on instead runs `getUserMedia` + MediaPipe Tasks Vision entirely outside any XR session, rendering into an ordinary transparent R3F `<Canvas>` layered over a `<video>` element. The two AR modes share the product's styled GLTF scene (via the extracted `useStyledScene` hook) and the concept of "bind a smoothed transform to a group," but have otherwise-independent rendering paths, camera setups, and lifecycle.
- **MediaPipe assets are self-hosted, not CDN-loaded.** Both the WASM runtime and the `.task` model files are committed under `public/mediapipe/` rather than pointed at Google's hosted URLs. Reason: matches this project's existing "everything the app needs to run should work without depending on a third party staying up" posture (same spirit as self-hosting fonts via `next/font`), and the spec explicitly asked for offline-demo capability. Trade-off: ~47 MB of binary assets committed to the repo.
- **Anchor hooks write to a ref, not React state, every detection tick.** `use-wrist-anchor.ts` / `use-foot-anchor.ts` run their own `requestVideoFrameCallback` loop at whatever rate `detectForVideo` can sustain (device-dependent, often 20-30 Hz) and store the latest computed transform in a ref that `TryOnScene`'s `useFrame` reads directly — calling `setState` at that rate would force a React re-render every tick for no benefit, since nothing in the render tree needs to change on a per-tick basis (only the R3F imperative scene graph does). `status` (which only transitions occasionally: loading → searching → tracking → lost) is the one thing mirrored into real state, since UI hint text does need to re-render on those transitions.
- **The 3D loader gates on `onFirstFrame`, not on `useGLTF` Suspense resolution.** `useGLTF` resolves the moment the binary is parsed, which is *before* the material upgrade in `ConfigurableModel` runs and *well before* the first frame is painted. Hooking the loader to Suspense would unmount it a few frames too early and leave the user staring at a momentarily-blank canvas. `onFirstFrame` runs inside the `useEffect` that follows the material-upgrade traversal — by that point the scene is ready to render and the very next R3F frameloop tick paints it. The loader's fade-out (300 ms `opacity` transition + 350 ms unmount delay) covers that single-frame window so the model genuinely "fades in" rather than popping.
